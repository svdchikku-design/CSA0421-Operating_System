Your CPU can leak secrets

In January 2018, Spectre and Meltdown showed that the speed tricks inside modern CPUs can be abused to read memory that should be off-limits.

Understanding and Detection of Attacks

How the attacks work, where they hurt, and how to spot them.

A. How the attacks work (slide 4)

Meltdown

Breaks the wall between user programs and the kernel, so an ordinary app may try to read kernel memory.

Spectre

Trains the branch predictor to trick a victim program, or another VM, into leaking its own memory.

B. Live lab: cache timing side-channel (Flush+Reload)

Type any secret. The “victim” speculatively touches one cache line per byte; the “attacker” times all 256 lines and the fastest one reveals the byte. Change the numbers and re-run.

Probe array — 256 cache lines (hover a cell). Green = fast = was accessed.

What it isFlush all lines → victim reads secret speculatively and touches probe[secret] → attacker times every line.
What happensHit ≈ fast, miss ≈ slow. If the gap is larger than the noise, the byte is recovered; with protection ON no fast line exists.

Try the lab: with protection ON nothing is brought into the cache, so every line is slow and the attacker gets nothing. In real life we detect it through cache-miss spikes, repeated flush+reload and abnormal branch misprediction.”

Result: one design covers all three variants. 

  

  
What to say
“While an app runs, the kernel is not in its page table at all, so Meltdown finds nothing to read. On every syscall we switch to the kernel table using a tagged TLB so we don’t pay a full flush. Inside the kernel we mask array indexes and fence risky branches for Spectre V1, and flush the predictor on return for Spectre V2. Turn a switch off here and you see the attack succeed.”

Conclusion and future scope

  

    
Key takeaways

      
✅ Spectre and Meltdown abuse speculation, not coding bugs

      
✅ KTPT hides the kernel by splitting page tables

      
✅ Masking, fences and predictor flushes cover Spectre

      
✅ Overhead stays manageable with PCID tagging

    

    
Future scope

      
🔹 Hardware-level fixes in newer CPUs

      
🔹 ML-based real-time attack detection

      
🔹 Testing on ARM, RISC-V and containers
